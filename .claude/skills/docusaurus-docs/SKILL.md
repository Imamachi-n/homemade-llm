# Docusaurus 技術ドキュメント執筆

Docusaurus の MDX は「Markdown のように見えて中身は JSX」なので、普通の Markdown 感覚で書くと
**ビルドは成功するのに表示だけ壊れる**（admonition が生テキストで出る、SVG が消える、数式が斜体ラテン体になる）
という事故が起きやすい。このスキルは、その地雷を踏まずに読みやすい技術ドキュメントを書くためのもの。

中心になる作業は次の流れ：

1. **プロジェクトの規約を把握する**（数式・図のプラグインが有効か、書式の流儀）
2. **読者に合わせて中身を組み立てる**（解説系なら「直感 → 定義 → 例 → コード → つながり」）
3. **MDX の作法どおりに書く**（KaTeX / admonition / SVG / コード）
4. **必ずビルドで検証して、警告まで潰す**

---

## 1. まず最初に：プロジェクトの規約を把握する

書き始める前に、そのサイトが何を使えるのか・どう書く流儀なのかを必ず確認する。これを飛ばすと
「数式が使えると思ったら設定が無かった」「文体がバラバラ」になる。

確認するもの：

- **`docusaurus.config.*`**
  - 数式: `remark-math` + `rehype-katex` が `presets` の docs に設定されているか。KaTeX の CSS が
    `stylesheets` で読み込まれているか。なければ数式は使えない。
  - 図: `markdown.mermaid: true` と `@docusaurus/theme-mermaid` があるか。
  - 高速化: `future.faster`（3.10 以降）/ `future.experimental_faster`（3.9 以前）の有無。
  - バージョン（`package.json` の `@docusaurus/core`）。3.10 で `future.experimental_faster` が
    `future.faster` に改名されるなど、版によって config の書き方が変わる。
- **`sidebars.*`**: 自動生成（`autogenerated`）か手動か。自動なら `sidebar_position` で順序が決まる。
- **`docusaurus.config.*` の `footer.links` / `navbar.items`**: ここに**ドキュメントへのリンクを手書きで
  並べている**サイトがある（`to: '/docs/...'` のリスト）。サイドバーが自動生成でも、**フッターやナビのリンクは
  自動では増えない**。
- **既存の代表ドキュメント1〜2本**: frontmatter の書き方（`sidebar_position` / `title`）、見出しレベル、
  文体（です・ます調か、だ・である調か）、admonition やコードブロックの使い方。**既存ファイルの文体・粒度に合わせる**。
- **パッケージマネージャ**: `pnpm-lock.yaml` / `package-lock.json` / `yarn.lock` のどれがあるか
  （ビルドコマンドが変わる）。

モノレポではドキュメントが `packages/.../docs` のように深い場所にあることが多い。ビルドはその
パッケージのディレクトリで実行する。

:::warning[新しいページを追加したら、ナビゲーションも更新する]

`.md` / `.mdx` を新規追加して終わり、にしない。サイドバーが `autogenerated` でも、**`docusaurus.config.*` の
`footer.links` や `navbar.items` に手書きされたリンク一覧には自動で載らない**ため、そこへの追記を忘れると
「サイドバーには出るのにフッター/ヘッダーに章が出ない」という取りこぼしになる（`onBrokenLinks: 'throw'` でも
リンクが**無い**だけなのでビルドは通り、気づきにくい）。新ページを足したら、(1) サイドバー（自動なら不要）、
(2) フッターの手書きリンク、(3) ナビバーの手書きリンク、(4) 既存ページからの「次の章へ」リンク、を確認する。

:::

## 2. 解説の組み立て方（チュートリアル・説明系の場合）

リファレンスではなく「分かるように説明する」タイプのドキュメントでは、各トピックを次の流れで書くと
初学者がついてこられる。むやみに定義から入らず、まず「何のためにあるのか」を渡すのがコツ。

1. **直感** — その概念が何のためにあるのかをイメージで（むずかしい言葉を使わずに）
2. **定義 / 数式** — 正確な形を示す
3. **具体例** — 実際の値・入力で手を動かして確かめる
4. **コード** — 実装ではどう書くか（言語に合わせて）
5. **つながり** — それがこのプロジェクト/分野の全体像のどこに効くのか

数式や記号を「説明なしで」出さないこと。新しい記号（例：$\cos\theta$、$\sum$、$|\boldsymbol{a}|$）は
**初めて使う直前で**意味を渡す。読者が手を止める場所はたいてい「いきなり出てきた記号・式」なので、
詰まりそうな所には小さな図や `:::note` で補足を足す。長い証明や寄り道は本文を分断するので、後述の
admonition コラムや `<details>` に逃がすと本筋が読みやすい。

## 3. KaTeX 数式

`remark-math` + `rehype-katex` が有効なら、インラインは `$...$`、ブロック（中央寄せの別行）は `$$...$$` で書ける。

```markdown
インライン: 内積は $\boldsymbol{a}\cdot\boldsymbol{b} = \sum_i a_i b_i$ です。

$$
\text{softmax}(a_i) = \frac{e^{a_i}}{\sum_j e^{a_j}}
$$
```

複数行そろえる式は `\begin{aligned} ... \end{aligned}` を `$$ ... $$` の中で使う。

### ハマりどころ（KaTeX）

- **数式の中に日本語など非ラテン文字を直接書かない。** KaTeX は数式モードで CJK 文字や丸数字
  （①②）を「未知の文字」として警告し、斜体の変な表示になる。ラベルに日本語を入れたいときは
  `\text{猫}` のように `\text{}` で囲む。丸数字 ①② は `\text{}` でも警告が出るので、式番号は
  `(1)` `(2)` のように**半角の括弧＋数字**にする。
- **Markdown テーブルのセル内で `|a|` と書かない。** 縦棒 `|` が列区切りと衝突して表が崩れる。
  絶対値・ノルムは `\lvert a \rvert`（`\lVert` でも可）を使う。表の外なら `$|a|$` でよい。
- 数式が表示されない／設定が無いときは、`docusaurus.config.*` の `remarkPlugins`/`rehypePlugins` と
  KaTeX CSS の読み込みを確認する。

## 4. Markdown の強調（太字）と日本語 — 見えない表示崩れ

`**太字**` `*斜体*` は、**閉じ記号の隣にある文字次第で「閉じられず」、`**` が生文字のまま表示される**ことがある。
日本語ドキュメントで特に踏みやすく、しかも **ビルドは `[SUCCESS]` のまま通る**（エラーにならない）ので、
HTML やブラウザで見るまで気づけない。原因は CommonMark の **フランキング規則**（強調記号が開け／閉じできる条件）と
日本語の約物（`（）「」』】、。` などの全角記号）の相性。

### いちばん多い壊れ方：太字が「閉じ括弧・閉じ引用」で終わる

CommonMark は、CJK の約物（全角の括弧・かぎ括弧・読点など）を**句読点**として扱う。閉じる `**` が
**「閉じ括弧 `）` や 閉じかぎ `」` の直後」かつ「その次が日本語の文字」**だと、閉じ記号として認識されず、
強調全体が成立しない（`**` が生で残る）。

```markdown
❌ これは**注目度の配分（棒グラフ）**です   → 「）」の直後の ** が閉じられず、** が文字で出る
❌ 役割は**「情報を混ぜ合わせる」**ことだ   → 「」の直後の ** も同様に壊れる

✅ これは**注目度の配分**（棒グラフ）です   → 括弧を太字の外に出す
✅ 役割は「**情報を混ぜ合わせる**」ことだ   → 引用符を太字の外に出す
```

直し方は2択。意味を変えずに直せる：

- **括弧の補足（グロス）を太字の外に出す**：`**用語（説明）**` → `**用語**（説明）`
- **引用符を太字の外に出す**：`**「フレーズ」**` → `「**フレーズ**」`

逆方向（開く `**` の直後が `（「` などで、その手前が日本語の文字）でも同じ理由で開けなくなる。
いずれも「**`**` を全角の約物に直接隣接させない**」のが原則。半角スペースや読点 `、` を挟めば成立するが、
日本語では不自然になりやすいので、上のように約物を強調の外へ出すのが読みやすい。

### 検出：ビルド後の HTML に生 `**` が残っていないか見る

目視では見落とすので、ビルド後の HTML を機械的にチェックするのが確実。**コードブロック内の `**`**
（Python の冪乗 `d_k ** 0.5` など）を巻き込まないよう、`<code>`／構文ハイライト由来のものは除外する。

```bash
# ビルド後。該当ページの index.html に生の ** が残っていれば壊れた強調（0 件が正常）
python3 - <<'PY'
import re
html = open('build/docs/<該当パス>/index.html', encoding='utf-8').read()
bad = []
for m in re.finditer(r'\*\*', html):
    i = m.start(); seg = html[max(0, i-80):i+30]
    if 'code>' in seg or 'token' in seg:   # コード/ハイライト内の ** は除外
        continue
    bad.append(repr(html[max(0, i-25):i+25]))
print(f'壊れ太字 {len(bad)} 件')
for b in bad: print('  ', b)
PY
```

1 件でも出たら、その前後の `）**` / `」**` / `**（` を上の方法で直して再ビルドする。**1ページで見つかったら、
同じ書き癖で他ページも壊れている**ことが多いので、全ページに対して走らせる。

## 5. admonition（注記・コラム）

`:::note` `:::tip` `:::warning` `:::info` `:::danger` で囲んだブロックは、色付きのコールアウトになる。
注意・補足・つまずきポイント・寄り道のコラムに使うと本文が締まる。

**タイトルはブラケット構文で書く。** これが一番のハマりどころ：

```markdown
:::tip[タイトルをここに]

本文。前後に空行を入れること。`$...$` の数式やリスト、コードも入れられる。

:::
```

- ❌ `:::note タイトル`（スペース区切り）… Docusaurus 3.10 以降では**認識されず、`:::note` が生テキストの
  まま表示される**。古い版では通っていたため、版を上げた途端に壊れることがある。
- ✅ `:::note[タイトル]`（ブラケット）… これが正式な構文。タイトル無しの `:::note` 単体は常にOK。
- 開始 `:::xxx` と本文、閉じ `:::` の前後に**空行**を入れる。
- 長い証明・派生的な解説は `:::tip[コラム：〜]` や `<details>` に入れて本筋から分離すると読みやすい。

ビルド後に生の `:::note` が HTML に残っていたら、それは認識されていない（タイトル構文ミスが大半）。

## 6. インライン SVG 図解

図は理解を一気に助ける。フローチャートや関係図は Mermaid（` ```mermaid ` フェンス）で手軽に描けるが、
グラフ・幾何・座標を細かく制御したい図解は **自前のインライン SVG** が確実で、色もレイアウトも自由。
ただし MDX では SVG/HTML は **JSX として解釈される**ので、普通の HTML 感覚で書くとコンパイルエラーになる。

### まず「何を1つ伝えるか」を決める（テンプレ選びより先に）

図は飾りではなく「**読者がいちばん詰まる1点を、絵で一撃で分からせる**」ための道具。だから描き始める前に、
順番に決める：

1. **この図で伝えたい核心は1つに絞る。** 「内積が大きい＝同じ向き」「softmax がスコア差を強調する」
   「頭ごとに注目先が違う」——1図1メッセージ。盛り込みすぎた図は何も伝わらない。複数言いたいなら図を分ける。
2. **その核心に最適な"見せ方"を、形から自由に発想する。** 大小なら棒グラフ、流れ・依存ならボックス＋矢印、
   幾何・角度なら座標、対応関係なら2列を線で結ぶ、変化なら before→after の並置、分布なら数直線＋帯……。
   **テンプレの7種に存在しない図でも、核心が伝わるなら新しく組んでよい**（今回の Attention フロー図や
   多頭の注目分布の対比のように)。「どのテンプレに当てはめるか」ではなく「何の形が一番伝わるか」で選ぶ。
3. **その形を、cookbook の部品（座標軸・矢印マーカー・グリッド・棒・曲線）で組み立てる。** 発想は自由に、
   実装は実証済みの部品で——これが速くて壊れないコツ。

迷ったら「言葉で3行かかる説明が、図なら一目になるか？」を基準にする。ならない図は描かない方がよい。

### JSX として書くときの必須ルール

- 属性は **camelCase**：`strokeWidth` `strokeDasharray` `textAnchor` `fontSize` `fillOpacity`
  `strokeOpacity`（`stroke-width` などハイフン形は不可）。
- `class` ではなく `className`。
- `style` は**文字列ではなくオブジェクト**：`style={{margin: '1rem auto', textAlign: 'center'}}`。
- すべてのタグを閉じる（`<line ... />`）。HTML コメント `<!-- -->` は使わない（JSX では `{/* */}`）。
- **SVG の `<text>` の中に `$...$` の数式を書かない。** remark-math がそれを KaTeX の `<span>` に変換し、
  SVG（foreign namespace）の中に `<span>` が紛れ込んで、ビルドが警告を出す（`HTML start tag "span" in a
  foreign namespace context` / `Stray end tag "text"`）。**ビルドが `[SUCCESS]` でも警告として出るので見逃しやすい。**
  SVG 内では数式記号もプレーン文字で書く：`W_O`、`d_k`、`√dₖ`（Unicode の下付き `ₖ` や記号で代用）。
  本物の数式で見せたいラベルは、SVG の外の `<figcaption>` 側に `$...$` で書く（figcaption は通常の MDX なので数式が効く）。

### テーマ（ダーク/ライト）対応

線や文字は `stroke="currentColor"` / `fill="currentColor"` にすると、本文の文字色を継ぐので
**ライトでもダークでも見える**。強調したい要素だけ、両テーマで視認できるアクセント色を使う
（例：青 `#3B82F6`・赤 `#EF4444`・緑 `#10B981`）。背景前提の固定色（真っ黒・真っ白）は避ける。

### 体裁

`<figure>` で包み、`<figcaption>` で一言キャプションを付ける。横並びにしたいときは
`<div style={{display: 'flex', flexWrap: 'wrap', gap: '1.5rem', justifyContent: 'center'}}>` でラップ。

**図の"部品集"として [references/svg-figure-cookbook.md](references/svg-figure-cookbook.md) を用意してある**
（座標軸・単位円・直角三角形・なす角・関数曲線＋接線・棒グラフ・行列グリッド、それに矢印マーカーや弧の描き方）。
図を描くときはまずここを読む。ただしこれは **「当てはめるテンプレ集」ではなく「組み合わせて使う実証済みの部品集」**
として扱う：

- **そのまま合う図** … 座標・色・ラベルを調整して流用する（速くて確実）。
- **合う形が無い図** … 上の「何を1つ伝えるか」で決めた最適な形を、cookbook の部品を**組み合わせて自作する**。
  ボックス＋矢印のフロー図、2列を線で結ぶ対応図、分布の並置比較など、部品の組み合わせでたいてい作れる。
  完全に新しい図を発想してもよい——**縛りは「核心が一目で伝わること」と、下のテーマ追従・JSX 作法・数式を SVG に
  入れないこと**だけ。発想は自由に、実装は cookbook の部品で固めると、速く・壊れにくく・想像力も活かせる。

新しく有用な図のパターンを作ったら、cookbook に1エントリ足して次回以降の部品にすると育っていく。

注：エディタの Markdown linter は SVG の各要素に `MD033/no-inline-html` 警告を出すが、これは
**無害**（SVG を使う以上は不可避）。ビルドが通っていれば気にしない。

## 7. 必ずビルドで検証する

MDX のエラーや表示崩れは書いただけでは気づけない。**編集が終わったら必ずビルドを実行**し、
成功と「警告ゼロ」まで確認する。

```bash
# パッケージマネージャ・ディレクトリはプロジェクトに合わせる
pnpm build      # or: npm run build / yarn build
```

確認ポイント：

- `[SUCCESS] Generated static files` が出る（=MDX/JSX がコンパイルできた）。
- **KaTeX 警告が無い**：`unicodeTextInMathMode` / `unknownSymbol` が出たら、数式内の日本語・記号を
  `\text{}` で囲むか別表記に直す（3節）。
- **admonition が効いている**：ビルド出力の HTML に生の `:::note` / `:::tip` が残っていないか確認する。
  残っていればタイトル構文ミス（5節）。
- **SVG 内に数式を入れていない**：`HTML start tag "span" in a foreign namespace context` /
  `Stray end tag "text"` が出たら、SVG の `<text>` 内の `$...$` が原因（6節）。`[SUCCESS]` でも警告として
  出るので、出力の warnings を必ず読む。プレーン文字に直すか、ラベルを figcaption 側へ移す。
- **強調が壊れていない**：ビルド後の HTML に生の `**` が残っていないか確認する（4節）。残っていれば
  日本語の約物に隣接した太字が閉じられていない。**ビルドはエラーにならない**ので必ず HTML 側で見る。
- リンク切れ等のエラー（`onBrokenLinks: 'throw'` のサイトはビルドが落ちる）。

簡単なチェック例（ビルド後）：

```bash
# 生の admonition が漏れていないか（0 件が正常）
grep -oc ':::note\|:::tip\|:::warning' <build出力>/<該当ページ>/index.html
```

最終的な見た目（SVG・数式・折りたたみ・ダーク/ライト）は `pnpm start` で開いて目視確認するのが確実。
特に Mermaid 図はクライアント側でレンダリングされ、ビルド後の HTML に定義が出ないことがあるので、ブラウザで確認する。
